# V2.6 recon — email (vmail) clue injection

**Branch:** `v2` · **Date:** 2026-09-15 · Companion to `docs/v2.5-handover.md` and the auto-loaded memory.
Trust this, but **verify any symbol before relying on it** (interop = accurate signatures, NO method bodies;
learn real behaviour at runtime). Decompiles this session in scratchpad `decomp-email/` (full project decompile
in `decomp-email/proj/`, one file per type — regenerate with `ilspycmd` if stale).

**Goal (from V2.5 "NEXT"):** some clues arrive as **emails** in an NPC inbox instead of as a physical note —
each eligible clue randomly EITHER physical OR email (never both). Eligible: Affair, Promotion, Layoffs,
Eviction. Excluded: RentArrears/Feud/Debt (their leads are handwriting + fingerprint, which an email can't
carry). The email version MUST keep NAMING the same people/addresses (Promotion/Layoffs/Eviction rely on the
clue for suspect identity).

**VERDICT: there IS a clean vmail-injection API** (the early "no clean email API" note is obsolete). The path
is `Toolbox.NewVmailThread(...)` + a custom `vmail`-type DDS tree (our existing custom-doc engine, retargeted
to `TreeType.vmail`). Threads **persist natively** in the save — simpler than physical notes.

## Data model — `StateSaveData.MessageThreadSave`
A vmail thread (one conversation, 1+ messages). Fields (all verified in interop):
- `int threadID` — unique; assigned from `StateSaveData.assignMessageThreadID`.
- `DDSSaveClasses.TreeType msgType` — **vmail = 1** (confirmed by memory AND a real asset `"treeType":1`).
- `string treeID` — the DDS tree that supplies the message body/layout (a `TreeType.vmail` tree).
- `int participantA/B/C/D` — humanIDs (A = from, B = to, C/D optional).
- `List<int> cc` — CC humanIDs.
- `List<string> messages` — per-message content refs (message instanceIDs into the tree).
- `List<int> senders` / `List<int> recievers` — humanID per message (parallel to `messages`).
- `List<float> timestamps` — per-message time.
- `float time` — thread time.
- `CustomDataSource ds` (`{sender, groupID}`) + `int dsID` — how `|token|` replacements resolve. We BAKE
  literal names, so `sender` / -1 is fine (token resolution irrelevant).

## Storage & access
- **Per-NPC inbox** = three `List<MessageThreadSave>` on `Human`: **`messageThreadsStarted`**,
  **`messageThreadFeatures`**, **`messageThreadCCd`**. A person sees threads they started, feature in
  (received), or are CC'd on → an email FROM boss TO promotee shows in BOTH inboxes (two chances to find it).
- **Central map** = `GameplayController.Instance.messageThreads` : `Dictionary<int, MessageThreadSave>`.
- **Native persistence** = `StateSaveData.messageThreads` : `List<MessageThreadSave>` + `assignMessageThreadID`
  → threads round-trip through save/reload for free. (Only the custom DDS tree the thread's `treeID` points at
  is runtime-only and must be re-registered on reload — same tree-rebuild the physical-note sidecar already
  does, but keyed by the thread's `treeID` string, not an Interactable id.)
- **Reading** = the **computer** (`VMailApp : CruncherAppContent` — an in-OS app, NOT the document reader; the
  old "vmail tree = blank page" caveat was about the *document* reader only). The vmail app renders the
  selected thread's `emailSender`/`emailReciever` (Human) + `emailTextContent` (string) + `tree` (DDSTreeSave).
  Player reads an NPC's vmail by accessing that NPC's computer (home/office; login friction is the point —
  the player checks inboxes when the physical clue isn't there).
- **Print path** = `VMailApp.PrintButton()` → `EvidencePrintedVmail : Evidence` (holds `threadID`,
  `msgIndexID`, `thread`); rendered via `WindowContentController.printedVmailDoc` (a DDSTreeSave). So a vmail
  can also become a physical, board-pinnable printout.

## Injection API (the linchpin) — `Toolbox`
```
// overload A (returns the thread):
StateSaveData.MessageThreadSave NewVmailThread(
    Human from, Human to1, Human to2, Human to3, List<Human> cc,
    string treeID, float timeStamp, int progress = 999,
    StateSaveData.CustomDataSource overrideDataSource = sender, int newDataSourceID = -1)
// overload B (void): NewVmailThread(Human from, List<Human> otherParticipiants, string treeID, float timeStamp, ...)
```
Given a sender, recipients, and a **DDS treeID**, the game builds the thread, wires participants, and (expected)
adds it to inboxes + `messageThreads`. `progress` (default 999) ≈ how many of the tree's messages are
delivered/revealed. We pass explicit Humans, so the tree's participant `connection` requirements +
`Toolbox.GetVmailParticipant`/`GetVmailGroupParticiapnts` (the game's own random-participant resolvers) are
bypassed. Related: `Toolbox.ProgressVmailThread(thread, addProgress)`, `Human.GeneratePastVmails()` (the
sandbox back-history generator — runs at citizen gen, long before our murder-time injection, so no conflict).

## vmail DDS tree shape (copy this)
Real vmail tree (`Player_ElGen`, `013ececf-…`): `treeType:1`; one `messages[0]` with `msgID` (block-bearing
message), `saidBy:0` (participantA=from), `saidTo:1` (participantB=to), `font:"Halogen"`, `fontSize:22`,
`usePages:false`, `isHandwriting:false`, `links:[]`; `document:{background:"", fill:1, size(0,0), colour white}`;
`startingMessage` = that message's instanceID. Body text lives in the message→block→**Strings `dds.blocks`**
table (SAME pipeline our `RegisterCustomDocTree` uses via `Strings.LoadIntoDictionary`). So the email engine =
`RegisterCustomDocTree` with `treeType=vmail`, `saidBy/saidTo` set, Halogen/22, `document.fill=1`.

## Design decisions still to make (per type)
An email needs a `from` and a `to`. The identity-carrying document of each eligible type maps to a vmail:
- **Layoffs** → the redundancy LIST (names all laid-off = suspects) as a vmail. Cleanest map. From = boss.
  To = ? (boss→boss draft in Sent, or boss→one laid-off, or boss→an HR contact). **Recommend boss→victim.**
- **Eviction** → the redevelopment PLAN (names property addresses → tenants) as a vmail. From = landlord.
  To = ? (a confidential plan; landlord→landlord draft, or landlord→a developer/accomplice). **Recommend a
  self-draft (landlord in Sent) or landlord→victim.**
- **Affair** → the love letter (lover A → lover B) as a vmail. Identity is redundant (gossip also names), so
  low-stakes. from=A, to=B. Vanilla affair trees are `document`-type, so build a CUSTOM vmail body.
- **Promotion** → the promotion LETTER (boss → promotee, names promotee) as a vmail. **The rival THREAT notes
  stay PHYSICAL** (anonymous handwriting + each rival's prints = the suspect-identity lead an email can't
  carry — same reason feud/debt are excluded). So only the letter forks to email.
- **Board connections:** physical custom notes draw doc→citizen/location facts (`CreateFact`/`AddCitizenConnection`).
  Whether an in-computer vmail supports the same board "connections" tab is a **runtime unknown** — but the
  BAKED clickable `<link>` names/addresses in the body are the guaranteed identity channel (TMP rich-text
  renders in `vmailBodyText`, expected to work as it does in the doc reader — verify at runtime). `EvidencePrintedVmail`
  is an `Evidence` so a *printed* copy can carry facts if needed.

## ✅ RESULT — WORKING RECIPE (verified in-game 2026-09-15)
The F3 test email delivers to the inbox, the body renders, it prints (`EvidencePrintedVmail`), and every clickable
`<link>` citizen link resolves. **The exact recipe that works:**
1. Build a custom **vmail** DDS tree = `RegisterCustomDocTree(body, asVmail:true)` which now sets, in addition to
   the document path: `treeType = vmail`; **`triggerPoint = TriggerPoint.vmail`** (a document/`onNewTrackTarget`
   triggerPoint delivers **0** messages — THIS was the whole bug); `repeat = RepeatSetting.sixHours`; four real
   **`DDSParticipant`** objects on `participantA..D` (null participants **crash** the inbox list renderer —
   blank list + locked cursor); message `saidBy=0`/`saidTo=1`, `font "Halogen"`, `fontSize 22`, `col` black,
   `usePages=false`; **`tree.messageRef[startingInstance] = messageSettings`** (the game builds messageRef when
   loading a tree from JSON; our runtime `AddMessage` leaves it empty, and the delivery walk needs it to resolve
   the starting message); `treeChance` stays 0 so the auto-vmail generator never picks our tree.
2. `Toolbox.Instance.NewVmailThread(from, to, null, null, emptyCcList, treeId, gameTime-24, 999, CustomDataSource.sender, -1)`
   → **delivers `msgs=1` on creation** (confirmed: first diag line showed `msgs=1 senders=1 recievers=1 times=1`,
   no ProgressVmailThread/hand-populate needed) and files the thread into `to.messageThreadFeatures` +
   `from.messageThreadsStarted` + `GameplayController.messageThreads`. Read on either participant's home computer.
The `ProgressVmailThread(999)` nudge + hand-populate + inbox-filing fallbacks in `InjectEmail` never fired (the
clean path works); keep as belt-and-suspenders or trim in cleanup. Diagnostics (`email[diag]`/`email[ref]`) can
be trimmed once per-type wiring is in.

**Inbox LIST row From:/To: subtitle — SOLVED (2026-09-15, verified in-game).** Root-caused by decompiling
`VMailApp.OnSetup` with Cpp2IL (IL-recovery + ISIL; interop = stubs only; tool + dumps in scratchpad `cpp2il/`).
The list row is ONE string `"<preview>\n<alpha=#AA>From: <name>"` (or `To: <name>` when sender=owner), and the
row **splits on the first newline** into title (elementText) vs. dimmed subtitle (elementText2). The `<preview>`
comes from `Human.ParseDDSMessage`'s **FIRST block**. Our vmail body was a SINGLE block, so the preview was our
ENTIRE multi-line body — its own newlines pushed the "From: <name>" past the split, leaving the subtitle blank.
Vanilla messages (e.g. `Work_Dinner`) have MULTIPLE short blocks, so their first block is one clean line.
**FIX (in `RegisterCustomDocTree` asVmail path): split the body into block0 = the first line (a clean, newline-
free preview/subject) + block1 = the remaining body.** `ParseDDSMessage`'s first element is then block0 (single
line) → the split works → subtitle renders `From:/To: <name>`; opening the mail still shows block0+block1 = the
full body with clickable links. (The earlier "runtime vs boot-loaded" hypothesis was WRONG — it was the
single-vs-multi-block preview all along. The `GetVmailSender`/`GetVmailReciever` name resolution + `Work_Dinner`
tree-field copy + `triggerPoint=vmail` + `messageRef` + participants were all necessary too, but the block-split
was the last missing piece.) So: author bodies so the FIRST LINE is a short subject/heading (our custom docs
already start with headings like "REDUNDANCY NOTICE"). Diagnostics used to find this (Harmony hooks on
`OnSetup`/`GetVmailSender`/`GetVmailReciever`, ref-thread dump, F2 vanilla-tree isolation, subtitle probe) have
been REMOVED post-fix.

## ✅ WIRED TO REAL CASES + RELOAD PERSISTENCE (2026-09-15, built + builds clean; NOT yet playtested)

The F3-proven engine is now wired into `ClueInjector.InjectForCase`'s per-type injectors as a **physical-OR-email
fork**, and injected vmail trees are re-registered on reload.

### Per-type fork (Affair/Layoffs/Eviction: never both — one coin flip per eligible clue)
- New config **`[Clues] EmailClueShare`** (default 0.5) + `ClueInjector.RollEmail()`. Governs Affair, Layoffs,
  Eviction. (Promotion is exempt — see below.) The fork is per-clue and independent, so a victim with several
  eligible events can, by chance, land all-email or all-physical — that's expected variance, not a bug.
- **Affair** (`InjectAffair`): love letter A→B → a **custom vmail body** (`BuildAffairEmailTree`, from=`ev.a`,
  to=`ev.b`; the physical version reuses a vanilla Infidelity *document* tree which can't be retargeted to vmail,
  so the email is a fresh body). Names both lovers as clickable links.
- **Layoffs** (`InjectLayoffs`): the redundancy list → email via `BuildRedundancyDocTree(..., asVmail:true)`.
  **`ev.a`=boss=victim, `ev.b`=null**, so it's a **self-draft** (from==to==boss), findable in the victim's own
  inbox; names all laid-off staff.
- **Eviction** (`InjectEviction`): the redevelopment plan → email via `BuildEvictionDocTree(..., asVmail:true)`.
  **`ev.a`=landlord=victim, `ev.b`=null** → **self-draft** (from==to==landlord); names the cleared property
  ADDRESSES (clickable location links).
- A failed email BUILD or DELIVERY **falls back to the physical note** (`InjectEmailClue` returns 0 → caller
  places the physical clue), so a case never ends up with no clue.

### Promotion — BOTH channels always (2026-09-16, redesigned after playtest)
Promotion does NOT coin-flip. It always emits **both**:
- **Physical rival threats** — one per passed-over rival, now a **custom anonymous handwritten note**
  (`BuildPromotionThreatDocTree` → `InjectAnonThreatNote`, kind `promothreat`): addressed **TO the victim**
  (clickable salutation), **FROM hidden**, carrying the rival's own handwriting + fingerprint — the feud/debt
  anon-note engine. This replaces the old vanilla `Dodgy_NoteRat` tree, which rendered generic "rat" text and
  drew a stray "To" (to a coworker, not the victim) plus a visible "From" that varied per suspect.
- **Email promotion letter** — always `BuildPromotionEmailTree` boss(`ev.b`)→promotee(`ev.a`), so it lands in
  **both** inboxes and is found whether the killer/victim is the boss or the promotee.

### Email timestamps
Each injected email is pre-dated by a **random** 6–120 in-game-hours (clamped ≥ 0; spread within elapsed time
early-game) in `InjectEmail`, so injected mails no longer all share one timestamp (the old fixed `gameTime−24h`).

### Excluded, always physical
RentArrears, Feud, Debt (handwriting + fingerprint leads email can't carry).
- `BuildRedundancyDocTree`/`BuildEvictionDocTree` gained a `bool asVmail` param (routes body → `BuildEmailBody`
  vs `RegisterCustomDocTree`); the existing physical-note callers + the note-reload rebuild path are unchanged
  (default `asVmail:false`). Emails do **not** draw board connections (the baked `<link>`s are the identity
  channel; connections-on-vmail stays an unverified unknown — printed vmails could carry facts if ever needed).

### Reload persistence (the definitive render-path finding)
**Cpp2IL (2022.1.0-pre-release.21, `--output-as dll_il_recovery`) decompile of `VMailApp.OnSetup` is decisive:**
it calls **`Human.ParseDDSMessage(string, …)` per message** and **`Strings.GetVmailSender(thread, int index, …)`** —
i.e. the vmail app renders each row from the **thread's stored `messages[i]` message-instance ids**, NOT from the
tree's `startingMessage`. And `Toolbox.NewVmailThread` (+ our `InjectEmail` fallback) store the tree's
`startingMessage` INTO `thread.messages[0]`. So after a reload:
- the thread round-trips natively (`StateSaveData.messageThreads`), keeping `messages[0]` = the **pre-reload**
  instance id;
- the custom DDS tree is rebuilt-at-boot-only → gone → re-registering it mints a **NEW** instance id;
- `ParseDDSMessage(old_inst)` finds nothing → **blank body**.

**FIX (two steps, both required):** on load, for each recorded email (new sidecar **`EM`** line: `treeId kind
fromId toId citizenIdsCsv`), (1) **re-register the custom vmail tree under the SAME `treeID`** — rebuilding the
same body via `RebuildEmailTree` (`BuildRedundancyDocTree/BuildEvictionDocTree(asVmail:true)`,
`BuildAffairEmailTree`, `BuildPromotionEmailTree`, `BuildTestEmailTree`) — then (2) **re-point the persisted
thread's `messages[0]`** at the freshly-minted `startingMessage` (`ClueInjector.ResyncThreadsForTree`, matching
threads by `treeID` in `GameplayController.messageThreads`). Step (2) is what makes `ParseDDSMessage` resolve the
rebuilt body. `senders`/`recievers`/`timestamps` are left as saved (only backfilled if empty).

Because the thread may not be restored into `messageThreads` at the exact tick citizens go live, the resync is
**retried each tick** (`Persistence._pendingEmailResync`) until the thread appears; the replay isn't "complete"
until every email is synced (or the whole replay times out at ~900 frames). Tree registration happens **once**
(no `Strings`-table spam). Sidecar is **back-compatible**: no `EM` lines → zero emails, older saves load clean.
The **F3 test email now persists too** (kind `testmail`) — F3 doubles as the email persistence test harness (like
F4 for physical notes).
